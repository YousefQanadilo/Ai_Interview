# Sprint 2 — Yousef's Prisma/SQLite persistence foundation

This branch adds the database models and **server-only** data-access functions for interview sessions. It does not change the React UI or implement HTTP routes. Franck can call the repository functions from his API.

## Why SQLite and Prisma?

SQLite is a simple local relational database that can be created on each teammate's computer without a paid service. Prisma supplies typed queries, foreign keys and reproducible migrations. Each teammate uses the committed schema and seed script. The local `.db` file must **not** be committed. SQLite does not automatically synchronize data across machines.

## Entity design

- `Student`: optional student ownership of sessions; a session can exist before login is implemented
- `InterviewQuestion`: reusable question bank and expected keywords
- `InterviewSession`: role, domain, stage, timestamps and duration
- `InterviewResponse`: initial or follow-up answer, transcript, duration and cadence gap
- `DiagnosticEvaluation`: one evaluation per session; verdict, scores, rubric and next drill
- `RemediationAttempt`: repeatable improvement attempts with before/after mastery

`Student` and `InterviewQuestion` relationships use `SET NULL` on deletion, retaining session history. Responses, evaluations and remediation attempts are deleted with their parent session. The optional structured rubric and feedback fields are stored as JSON text because SQLite/Prisma does not expose native JSON columns in this chosen setup.

## Install and initialize (each teammate)

1. Switch to the Sprint 2 branch and run `npm install` (not `npm ci` until the lockfile has been regenerated and committed).
2. Add `DATABASE_URL="file:./dev.db"` to your local `.env` (never commit this file).
3. Run `npm run db:generate`.
4. Run `npm run db:migrate` to apply the committed migration.
5. Run `npm run db:seed` to create an illustrative, **unscored** demo record.
6. Run `npm run test:db` for isolated SQLite integration tests. Run `npm test`, `npm run lint` and `npm run build` for the existing checks.

The SQLite `file:./dev.db` URL is resolved relative to `prisma/schema.prisma`; it creates `prisma/dev.db`. Each developer should verify records locally with `npm run db:studio` or a repository function.

Before merging, regenerate and commit `package-lock.json` from the modified `package.json` using `npm install`. The lockfile has **not** been regenerated by this remote GitHub edit.

API routes must validate authentication and ownership before calling the repository. No endpoint is exposed on this branch.

## Tests and team verification

`npm run test:db` creates a uniquely named **temporary database** in `prisma/`, applies the migration, verifies writing and reading a session/response/evaluation across a client reconnect, tests invalid input, and deletes the database. It does not modify another teammate's database.

Add each person's verified local database operation to `docs/database-setup.md` when Lee prepares the team-wide instructions.

## Coordination and assumptions to review

- User authentication does not exist yet, so `studentId` is nullable. For production, require authenticated students and access control.
- Role, domain, stage, and verdict values are strings in SQL; validation occurs in repository functions. Consider SQL-level CHECK constraints for additional protection later.
- One diagnostic evaluation is associated with each session; a session can have multiple remediation attempts.
- Seed data is clearly labeled as a demo and is not a real interview result.
- UML class and sequence diagrams should use these model names and relationships.
- No database operations have yet been connected to the existing browser-localStorage history UI.
